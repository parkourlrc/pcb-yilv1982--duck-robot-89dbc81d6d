## 当前判断

**[推断] 当前最吻合的是：动作期间供电电压下降，触发 robotd 原有的低电压自动关机。**
证据分别是多舵机低电压遥测、实际配置继承的自动关机默认值、随后 Studio 与用户会话的有序停止记录。
但它们尚未构成直接的触发记录：**缺失故障启动周期的 robotd 和内核系统日志，也没有关机前平滑电压达到 6.6 V 的连续采样。**
因此不能宣称低压关机已证实，更不能将 3 A 限流、接头压降、HAT 降压故障或 CPU 过热定为根因。

**[实测] 当前配置与 Studio 提示确有差异；[源码核验] robotd 未设置该项时默认自动关机，Studio 未读到该项却显示“只警告”。**
这不是新恢复入口的 8 秒超时关机；恢复超时路径请求卸力，并不调用系统关机。

## 日志保留情况及排除边界

- **[实测]** Studio 文件 `/home/radxa/studio-dev/logs/studio-2026-11-01.log` 和用户 journal 保留下来，已复制到本项目。
- **[实测]** 提权后，故障 boot 的 `journalctl -u robotd` 无条目；系统专用 journal 的 boot 列表只有本次及 10-25 两个旧启动。`journalctl --system -b <故障boot>` 明确报告不存在该 boot。
- **[实测]** 当前 `system.journal` 的创建时间为新启动早期；未找到故障那次的 system 归档。journald 配置为默认 `Storage=auto`，有持久目录，故**不能简单归因为“没开持久日志”**。已核对 unit 与 tmpfiles 常规规则，日志为何丢失仍未确定。
- **[实测]** `/var/lib/systemd/pstore/console-ramoops-0` 修改日期为 **2026-10-25**，其 watchdog/reboot 行是历史记录，不能归给本次事故；本次 `/sys/fs/pstore` 为空。
- 未装 `coredumpctl`；检查范围未发现相关 core。故障 kernel 和 robotd 日志缺失，不能据“没搜到”排除 OOM、panic、温控关机或进程异常。
- CPU 部署前 81.111°C、部署验收后 80°C；重启后 00:04 为 70°C。现场 sysfs 的 passive 阈值为 75/85°C、critical 为 115°C。这些均非故障瞬间温度，不足以判定过热原因。
- 保存的 Studio 命令日志中，最后开始走至停止之间没有显式 `robot.shutdown`；仍不能排除其他客户端、系统电源事件或用户在停机前后的操作。
