## 通信数据与模型运行

对比同 boot 的 **00:04:24 快照 → 01:11:10 快照**，不是在动作前插入的新采样：

- SYNC_READ 不完整超时累计从 2 到 **1325**，增加 **1323**。
- ID 200 缺答增加 **1252**；舵机也有缺答，例如左膝 ID 23 增加 **400**、左踝 ID 24 增加 **377**。不能说“只有 IMU 坏、全部舵机一直正常”。
- IMU 重复数据计数增加 **2172**。这是重复块统计，不等同 2172 个 checksum 坏帧，也不保证每个都被拒绝。
- 控制周期 missed 增加 **1324**；缺答统计按 ID 分别累加，不能跨 ID 相加当总事务数。
- 动作日志中有 99 条 ID 200 超时警告、217 条 IMU 陈旧警告；日志合并计数，条数不等于实际失败总数。

`BusImuFreshness::check` 的统一错误文本覆盖 ready/age 条件和重复计数条件。
本机是 Feetech/legacy（ft6），错误文字里的 DXL2 是共用说明，**不表示本机切换了 DXL2**。
目前未记录故障时原始回复帧，不能将本次缺答/重复解释成以前 v0.3 的已捕获坏 checksum。
快照中 `sync.bad_checksums=0` 只属于最后一次成功事务，也不能据此断言整个故障期间零坏校验。

本次窗口没有 `robot.recover` 命令，原生 `walk_recovery` 仍为 idle、request_id=null。
用户看到的是普通 walk 已启用时的自动尝试；**网页躺姿恢复的 8 秒上限没有参与本次流程**。
普通 walk 的倒地标记不自动结束策略；失去反馈后改为保持，恢复后再推理，持续到明确停下或其他保护介入。
