## 本次选型建议（工程判断）

既有总线实验为1Mbps；以下是针对本项目数字通信故障定位的配置建议，不是通用最低仪器标准。到货后仍按实际串口设置核对。

| 项目 | 最低可用建议 | 推荐配置 | 本次用途 |
|---|---|---|---|
| 模拟通道 | 2通道 | **4通道** | 同次请求中对照DATA、IMU MCU RX、IMU MCU TX、主控RX；按物理布局必要时换测点 |
| 模拟带宽 | 50MHz | **70～100MHz** | 观察低位平台、上升/下降沿及明显振铃；不按1Mbps简单购买1MHz仪器 |
| 实时采样率 | 使用中的各通道≥250MSa/s较合适 | 标称最高≥1GSa/s，同时核对**四通道各≥250MSa/s** | 各通道共享采样资源时规格会下降，最高值不等于全开值 |
| 存储深度 | 每个使用中通道≥1Mpts | **四通道模式每通道≥5Mpts，10Mpts更好** | 一次保留完整请求和应答窗口后放大细节；实际记录时长=点数/实际采样率 |
| 解码/触发 | 单次捕获、边沿触发，能保存波形 | UART触发/解码、可设阈值，支持1Mbps及实际8N1配置；脉宽/欠幅触发和历史记录便于后续定位 | 解码字节与主机日志核对，不将任意脉冲视为有效指令 |
| 导出 | 截图 | 原生波形或CSV、截图、USB或LAN传输 | 后续离线核对，避免只有屏幕照片 |
| 探头 | 足额匹配带宽的无源探头 | 4支可设10×探头、短接地弹簧、细钩/绝缘附件 | 降低探头对信号的影响并避免密集焊点短接；到货后核实附件 |
| 垂直分辨率 | 8bit可作此类数字故障定位 | 12bit为加分项 | 对微小电压变化更细致，但本任务优先通道、触发、采样和探头 |

**取舍**：本任务更倾向4通道70MHz，而不是为了200MHz选2通道。50～100MHz档能推进微秒级串口和明显电平/时序异常定位，但不能保证准确还原所有数纳秒边沿或更高频振铃；若后续证据指向超出仪器带宽的问题再调整工具。不要求信号发生器、16路逻辑探头或高压差分探头套装来开始此项低压总线定位。

## 到货后的观测顺序与下一项处理

**先建立可对照捕获**：保持原接法和同一请求模式，优先复用单ID200读取，舵机挂线但不主动查询；先存一份10颗舵机的正常请求/应答，再捕获15颗时的失败请求。两组使用相同软件、波特率、读命令、供电和仪器设置，记录每次主机实际发送字节及成功/超时。初始用普通或单次采集，不用平均波形掩盖偶发事件。协议解码与模拟幅度/边沿都保留，截图之外保存原始记录；记录通道、衰减、采样率、时基、触发和探点。

下表是逻辑测点，**不是已核准的实物探针位置**。IMU公开PCB将U5第4脚接`/PA3_USART1_RX`，U4第2脚接`/PA2_USART1_TX`，已于本轮重新读取网表确认；本机焊点与方向须结合实物定位，不直接按照片上下数脚。HAT V1.2 MCU侧UART和收发器对应关系仍须实物核对。优先从安全的同网较大焊盘引出测点，不能在带电密脚间滑动探头。

| 用户要分开的阶段 | 必须看到的证据 | 结果对应的下一步 |
|---|---|---|
| ①请求没有正确到达IMU | 对照主机发送/外部DATA与IMU MCU RX；不只看连接器上有没有脉冲 | HAT输出已异常则查发送使能/驱动及负载；外部DATA正常但MCU RX失真则查IMU保护/接收缓冲；只针对出现差异的段测上下游 |
| ②请求到达但没有正确应答 | MCU RX上帧内容、校验、位时序与正常条件一致，同次观察MCU TX是否输出预期应答 | RX正确而TX没有预期输出，将范围转到UART接收/固件/运行与响应控制；检查实际开启的日志或制定最小诊断方案，不直接判传感器坏 |
| ③应答未通过总线到达主控 | MCU TX已有对应的有效应答，比较IMU外部DATA和HAT/主控RX | TX有而DATA无：查IMU输出/使能/保护路径；DATA有而主控RX无：查总线/HAT回程；主控RX也正确而软件超时：转主机UART/接收解析 |

**边界**：示波器看到正确请求到达MCU引脚，不等于UART外设或固件已经接受该帧；第②类需要内部状态才能进一步定固件根因。“TX无波形”还要结合波特率/触发窗、引脚复用和运行状态；没有对应波形前不预先判故障方向。有波形以后先定位异常段，再给出有依据的单项干预、验证和恢复方案。

**通道安排**：四通道初始候选为IMU外部DATA、IMU MCU RX、IMU MCU TX、HAT主控RX；若第①段缺请求，把一通道改到HAT发送前端；若第③段缺回包，再改到驱动使能。四通道也不覆盖所有节点，但可以把同一次请求的多个位置关联起来。双通道按DATA+RX、RX+TX、TX+DATA、DATA+主控RX分阶段，不能把不同时刻的两次偶发失败当同一次事件。

**接地准备**：实际型号到货后先核仪器和电脑/电源的接地方式。普通共地通道的地夹不能分别夹到电阻两端；本任务各探头参考接已确认的系统GND，探针碰信号，不接DATA或VBATT作“地”。测跨器件电压用两通道相对共同GND测量后相减，或适合的差分方法；不通过断开保护地来实现浮地。移动细小测点先断电、固定探点再上电；保留既定7.4V/3A限流及已确认针序，不新增无关上电验收。

## IMU 内部数据级调试：现有能力与第二阶段缺口

日期：2026-10-27。用户补充“IMU得支持数据级别的调试”。本节为排障规划和只读源码核对，不是诊断固件开发授权或已完成日志采集。

### 外部解码与内部处理要分开

| 证据 | 能回答的问题 | 不能单独推出 |
|---|---|---|
| 示波器在MCU RX脚的波形与UART解码 | 引脚上是否有与请求一致的电气帧、字节与时序 | MCU UART外设实际取到的字节、软件是否处理及为何丢弃；仪器和MCU采样条件也不完全相同 |
| UART实际接收记录 | 外设收到/软件读出了什么，有无溢出/帧错误等状态 | 这些字节已通过组帧/校验或进入指令处理 |
| 固件帧校验/处理及应答记录 | 哪次请求被接受、丢弃原因，是否生成/提交应答 | TX引脚实际发出且总线另一端收到；仍需与波形对应 |

**[判断]** 若目的是进一步解释“正确帧到RX脚后为什么没答”，需要内部状态/数据证据，通常由诊断日志、记录缓冲或可用调试器取得。它不要求原成品固件出厂就已有完整抓包功能，也不阻塞先用示波器缩小到输入或输出路径。只有序号/时间及成功失败能对应的记录才能关联同一次事务；累计计数可作初筛，不能自动当作逐帧证据。

### 已核对的能力（源码/上游记录，不是本机已启用）

- **H1为独立调试UART，H2为SWD**，依据[既有接口核对](../servo-web-imu-3d-20261024/debug-plan-20261026.md)。H1不是3P总线DATA。用户已有FT232H/DAPLink，但实物针序、接线及目标可访问性没有由本次只读核查确认。
- **公开 `firmware-1.5.1` 标签默认 `DBG_ENABLE=0`**，见[归档CMake](../microduck-imu-community-20261026/sources/jyg9-tag-1.5.1--CMakeLists.txt.txt)第31/72行附近与[标签来源/哈希](../microduck-imu-community-20261026/firmware-1.5.1-check.json)。这是编译开关，不能当成用户在运行界面里必可打开的设置；本机 `1.5.1 / CRC32 0xD9CA0DEF` 尚未匹配构建，不能保证开或关。
- **参考代码的默认状态行主要是统计，但并非完全没有事件日志**：`firmware/v1/src/main.c:164–175` 打印总线 `rx/tx/dropped/err/echo/frames/answered` 和 `lost/gaps/ignored`；TRACE 级别在 `dxl2.c:198` 有 DXL CRC 错误事件，`bus.c:120` 有同步读延迟事件。它们不提供完整的原始请求/应答快照，飞特校验失败分支也没有同等日志。结构中的 `bad_crc` 没有直接包含在默认状态输出中。详见下面固定 1.5.1 源码核查，不能把“默认统计不够”扩大成“固件完全不支持数据调试”。
- **错误/接收计数的定义须按具体构建核对**：归档[1.5.1 uart_port.c](../microduck-imu-community-20261026/sources/jyg9-tag-1.5.1--src--uart_port.c.txt)第158行在回声过滤前递增 `rx_bytes`，185行的 `rx_errors` 来自ORERR分支。因此不能把rx增加解释为新请求已被组帧，也不能把err=0解释为全部接收条件正常。
- **日志会影响被测时序**：上游[0456a83提交原件](../microduck-imu-community-20261026/commit-0456a83e863d.json)解释旧状态打印阻塞主循环并造成数据更新暂停，这是作者当时构建的观察，不是本机已重现实测。因此不能为抓故障直接在高速接收路径中逐字节阻塞打印或把“大量日志开启后没故障”当成修复。

来源URL均在上述原始档案/来源JSON中。本轮 `web.run` 打开官方1.5.1发布页无可读返回；依据是已有归档标签、作者提交与本地只读代码，没有新在线核验或本机日志采样。

### 需要的最小内部记录（设计建议，尚未实现）

1. **接收**：UART实际读取的字节或足以比对的一帧快照，接收长度、时间/事件序号及硬件错误状态；保留回声过滤前后差异的计数或丢弃原因。
2. **校验与分发**：帧是否完整、协议/ID/指令、校验结果，因长度/校验/地址/回声等丢弃的明确原因；因未收到任何字节而不存在记录的情况须用波形对应，不能虚构一帧事件。
3. **应答**：是否进入处理分支、是否生成应答及其字节、何时提交发送、忙/延后/丢弃原因与发送完成状态。软件发送完成不等于外部电气传输成功。
4. **运行/记录自身**：必要的复位或运行连续性标记、缓冲区溢出/记录丢失数。用短事件、有限RAM缓冲及批次结束后导出，或不会阻塞关键路径的限量输出；不让诊断数据挤占故障3P总线，不默认在接收中断内打印。具体机制还需匹配MCU资源与实际代码。

### 下一步与结果对应的处理

先保留原固件并准备示波器捕获，同时核实供板方的构建来源、是否支持上述诊断内容以及取得方式；这是可由用户核对的材料清单，未代发消息。已有状态日志若可用，先看短请求窗口中的计数差值，足以定位则不追加开发。若不足，再选匹配该板的诊断构建或制定最小插桩方案；**当前没有进入编码、刷写或断点调试**。

若后续要改固件，先明确原镜像/配置备份、对应源码、修改范围与恢复办法，尽量不混入功能升级；用未改固件保存原始故障基线，并确认诊断开启后同条件故障仍可复现。若考虑H2+SWD，需先确认访问保护、符号/地址与读取方式；插断点、暂停MCU会改变时序，DAPLink不是无需准备就能抓到历史逐字节日志的工具。

| 波形与内部记录组合 | 下一项处理 |
|---|---|
| RX脚帧已失真/缺失 | 按原波形计划定位输入链路，不以缺内部日志阻塞 |
| RX脚正确，UART记录缺字节/有错误 | 查UART配置、外设/中断接收及溢出；并保留引脚采样余量问题作为替代解释 |
| UART字节正确但组帧/校验/分发丢弃 | 按对应原因查接收状态机、过滤与协议处理 |
| 接受有效请求但未生成/提交应答 | 查指令分支、运行状态、等待/忙及响应控制 |
| 生成/提交应答而MCU TX或外部DATA异常 | 结合使能与TX波形继续区分发送驱动、引脚配置、时序和接口路径 |
| 总线回包及主控RX正确而主机软件超时 | 转主机UART缓冲与接收解析，不继续改IMU接收电阻 |

本轮确认的是调试能力缺口和推进条件，不是确认固件根因。原先三阶段计划继续有效，第②阶段细化为“引脚→UART实际接收→协议处理→生成/发送应答”。

## 固件是否开源，以及“不能保证”的具体含义

日期：2026-10-27。问题：用户追问当前单口 GD32 板是否开源、是否需要另找固件，以及 H1 日志为何不能直接确定可用。本节是源码/许可与可观测性核查，不是本机日志实测或刷机结果。

**[源码证据] 对应社区固件已开源。** `jyg9/microduck-community-kit/firmware/v1` 包含 GD32F303CC + LSM6DSV16X 的应用、总线协议、调试实现、bootloader 与构建工程；其 `LICENSE` 为 Apache License 2.0。此次通过 GitHub API 将 `firmware-1.5.1` 标签解析为提交 `142ca27a887b99e1231a6307394dce29df56d4bf`，下载固定提交原件。不是只有二进制或上位机源码。第三方 GD32 库另按其许可；本节不扩大解释整仓库所有文件许可。

**H1 是独立日志输出通道，不是总线收发字节的自动复制口。** 固件必须主动在需要的处理位置生成记录，再送到 USART0/H1。`BUS_MIRROR_ENABLE` 表示 H1 也作为协议服务口，并不表示自动镜像主总线流量，不能为抓包直接将其设为 1。

### 两个日志开关与实际内容

| 证据 | 固定 1.5.1 源码定位 | 对用户的具体含义 |
|---|---|---|
| 编译开关 `DBG_ENABLE` 默认 0 | `CMakeLists.txt:72`；`dbg.h:35–47`、`dbg.c:31–64` | 若本机按这个设置编译，日志代码已去掉，连接 H1 或改运行级别都不会恢复输出；需要含日志代码的构建 |
| 运行级别 `dbg_level` 可调，默认 2 | `dev_cfg.c:31`；`dev.c:137,263–265`；`dbg.h:22–24` | 只有编译时保留日志代码才有效；0 关闭、1 错误、2 统计、3 TRACE。不能把运行级别寄存器存在当日志代码存在 |
| 统计与少量 TRACE 事件 | `main.c:164–175`；`dxl2.c:198`；`bus.c:120` | 已有收/发/丢弃等累计统计及部分 DXL CRC/仲裁事件；上一轮只讲统计不够完整，本轮补正 |
| 尚无完整逐帧数据记录 | `dbg_hex` 仅有声明与实现，`dbg.h` 注释说明无调用点；`fee.c:81–88` 校验失败直接计数/退出 | 打开 TRACE 不等于得到每次飞特请求、丢弃原因与应答的完整字节；需补具体记录点才能满足本次定位需求 |

**“不能保证”现改为两个明确待确认项**：①本机镜像有没有编入并开启日志；②现有输出是否覆盖我们要定位的失败分支。接口和源码能力有直接证据，不能将这两个缺口说成“板子也许无法调试”。尚未在本机接 H1 取日志，不能报告它有或没有输出。

### 可推进的处理分支

- 本机已含日志代码：按匹配构建核运行级别，先用已有统计/事件；足以定位就不新增代码。
- 本机没有日志代码，或现有事件不足：以这套对应板型的公开源码为基础，制作只增加诊断的构建，记录 RX 字节、校验/丢弃原因、应答生成/提交，再经 H1 导出。当前尚未制作、刷入或验证此构建。
- 本机无法匹配到原始提交：先记录其可复现的原始故障与恢复材料，再把公开 1.5.1 当作明确版本的候选基线；替换后须复核故障仍可复现，不能把“换构建后好了”直接解释为某个诊断点修复。此项是后续方案，不阻塞先抓原固件波形。

**[工程判断] 不需要因为“源码不可得”另找固件。** 已归档的 ScrapMeta、fanhao375 和 kissqy 实现主要面向 STM32G031，MCU、引脚、启动/存储布局及协议细节不同，不能直接刷到本机 GD32F303；仅作为接收/协议实现参考，兼容边界见[替代项目来源与比较](../microduck-imu-community-20261026/research.md#其他复刻项目)。对本板优先使用 jyg9 工程核查和补诊断，工作副本应放本项目可写目录，参考库保持只读。

日志采用短事件/有限缓冲、限量或批后导出，避免现有阻塞打印改变故障条件。设计与恢复方案仍需后续明确，本轮没有编译、改代码、接线、写寄存器或刷机。
