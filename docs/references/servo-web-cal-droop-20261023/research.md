# servo-web CAL 后读数不是 2048 的问题诊断（2026-10-23）

## 问题与范围

用户反馈（2026-10-23）：servo-web 每行 CAL 按钮，摆好位置点击后**当前读数不是 2048**；期望"摆好的位置点 CAL 后读数就是 2048"。本轮先诊断（不动代码/舵机），后另有 2026-10-23 01:05 修复部署与复核记录（见文末）。

## 结论（一句话；2026-10-23 第二次勘误，以本节为准）

**真凶是旧版"下垂补偿"的符号错误，0x0B 固件指令本身是无辜的。** 0x0B 一直正确（当前位置→2048）；但随后旧代码用 `droop = pre − target + sign×Δ偏移` 算"下垂"并再挪一次偏移，`sign` 因探针失效默认 +1，而本机实际约定是 −1（读数=raw−偏移，2026-10-23 01:16–01:20 九次校准的偏移变化全部为 `−(target−pre)` 证实）。于是补偿把偏移又挪了 `2×(target−pre)` 的反向量，**最终读数 = 2×pre − 2048**。去掉补偿后（cal-fix 补丁），同一固件的 0x0B 连续九次直接落在 2048（method=0x0B、无兜底痕迹）。

### 勘误历史（保留追溯）

- 初稿：解释为"关扭矩重力下垂被补偿"——错。五次"下垂量"恒等于 2×(2048−pre)，是 pre 的纯函数，物理重力不可能。
- 第一次勘误（采信并行会话）：归因"HD-1910 3.46 的 0x0B 偏移符号写反"——也不对。该结论把"0x0B + 补偿"两步的合并结果当成了 0x0B 单级行为（当时只看了备份里 541→1356 的首尾值，1356 实为补偿写的那笔，0x0B 自己写的是正确的 −274 一档）。
- 本次（第二次勘误）：用今晚 01:16–01:20 九次"无补偿"校准（0x0B 全部一次到位）反证 0x0B 正确；符号错在补偿一步。cal-fix 补丁有效的原因：① 校验了 0x0B 后位置；② 关掉了真正的元凶（补偿）。

## 机制（上游 server.py `calibrate_one` 旧行为）

顺序：限速 → 解锁 → 读 `pre` → 关扭矩并回读 → `0x0B` → 轮询偏移落地 → 算 `droop = pre − target + sign×(off − o_before)` 并把偏移再挪 droop（"下垂补偿"）→ 目标寄存器写当前读数（防开扭矩跳）→ 开扭矩 → 加锁。三个缺陷叠加成现象：

1. **0x0B 写反**（固件 bug）：同物理位置读数变成 `2×pre − target`；
2. `ok` 判据只看"偏移变没变"，不回读 `pos==target`；
3. "下垂补偿"又按代数 droop 把偏移挪一次——恰好把读数停在 `2×pre−target` 不动（两种符号操作互相抵消一半），看起来像"垂了多少就差多少"。

复点会越来越偏：每次 pre=上次停点，最终读数=2×pre−2048 继续远离（#21 实测 1860→1668→1271；#22 1636→1224→418）。

另：符号探针（`probe_offset_sign` 写 +1 读数验证方向）在 `_calibrate_mid_all` 里**先于解锁**执行，31 号偏移在 EEPROM 锁区（5~39），锁着写被静默拒绝，所以每次都"偏移 +1 读数没变，方向未知"——不是步长问题，是时机问题（加大步长也探不出；应在解锁后探或删掉，兜底已两向都试）。
