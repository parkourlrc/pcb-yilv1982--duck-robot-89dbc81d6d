# 第二阶段：`--imu-bus` 启用后仍不出数——根因与修复（2026-10-24 下午，已完成）

## 现象

用户带 `--imu-bus` 重启后面板无数据；日志两类刷屏：

- `live/stale：IMU 融合还没出数（四元数全 0 / BIT0）`（常驻）
- `live/error：小板报告跟 IMU 芯片通信失败（BIT1…）`（约每 23–28 秒一次）

启动头几秒还有零星 `ID 200 连续 1 帧没应答`（伴随同帧舵机丢应答一次，随后降级逻辑自愈）。

## 排查与证据

1. **先纠正一个测量陷阱**：在 servo-web 占用 /dev/ttyS2 时另开进程读 200 会抢应答帧，
   得到假"无应答"。总线探测必须在停服后独占进行。
2. **干净探测（[scripts/imu200-diag.py](../../../scripts/imu200-diag.py)，停服后直读）**：
   当次成功样本有效——`flags=0x81`、陀螺真实噪声（约 -3..-7/23..27/11..15 raw）、加速度
   Z≈8150raw≈1g、采样计数在走（100 Hz 栅格）、四元数 half 位型解出 ≈(-0.009, +0.014, +0.463)
   （w=√(1−‖v‖²)≈0.886，模长 1，合法姿态）。厂商窗 magic 正确、`sim_mode=1`
   （真 SPI 构建下不改变数据源，flags 无 bit4=模拟器位，实测数据确为真传感器）。
3. **根因——状态位语义版本不匹配**：板②固件状态位是社区 kit imu_to_dxl v1 语义
   （协议文档 §6.4 + kit `host/bus.py` `TELEM_FLAG_BITS`：`bit0=sflp_valid 四元数有效`、
   `bit1=cnt_wrap 计数回绕`、`bit2=gyro_sat`、`bit3=sensor_err`、`bit4=simulated`、
   `bit7=fusion_ok`）；而 servo-web 的 `imu_bus.py` 沿用 duck-control 旧语义
   （`bit0=融合未就绪、bit1=通信失败、bit2=自检失败、bit3=读太慢`）。两套 bit0/bit1 含义相反：
   - 本板每帧 bit0 置位（=有效）→ 旧判据 `bits & 0x01` 命中"融合还没出数"→ **永远 stale，面板无数据**；
   - 100 Hz 采样计数每 2.56 s 回绕一次（bit1）→ 被当"通信失败"周期性刷 error。
4. 附带发现：诊断脚本 v1 的 half 解码有 bug（把 uint16 原始位型当整数值转半精度），已修为
   `struct.unpack("<e", struct.pack("<H", h))`；修后四元数即合法。

### 本机固件身份（首次补齐）

4 个成功身份块完全一致：`55 50 00 00 00 01 15 ef 0d ca d9 01 ff ff 00 00`。

- magic=`0x5055`，应用态、运行槽 A、flags=`0x00`。
- image_version=`0x1501`，按 major/minor/patch 位域解为 **1.5.1**。
- 镜像自报 CRC32=`0xD9CA0DEF`，身份扩展版本 1；boot_slot / trial_slot 都为 255，attempts / boot_stay 为 0。
- 这是身份窗回读，不是对整片 Flash 做了独立校验；尚未找到与该 CRC 对应的本地包，不能仅因本地 CMake 默认也是 1.5.1，就认定二进制与全部当前源码一致。

### 两个已确认的软件行为与一项旧归因勘误

1. **单帧缺失即显示断线**：`BusImuService.feed(None)` 每漏一帧立即发布 `disconnected`，下次有效块发布 `live`；累计 5 次才从常规读取中移出并改用 PING 探测。因而页面闪断不能换算成板子复位次数。
2. **超时提示和实际等待不一致**：部署版 `_read_status` 设置 `deadline = timeout * 3`，但 `serial.read(1)` 一次为空就 `break`；默认 timeout=0.02，所以没有帧头时约 20 ms 即可失败，提示却写 60 ms。前轮 13–19% timeout 不能当成已等满 60 ms。该缺陷尚未修改；本轮失败原始窗口达到 100/250 ms 仍没有字节，故不能认为单独延长超时就能根治。
3. **撤销 `bad_id = 垃圾帧 = IMU 主动压线` 的“终案”**：接收器先校验 checksum，之后才在 `收到的 sid != expect_id` 时加 bad_id。此计数通常表示一帧校验通过但 ID 与当前期待不符的包；按预定顺序逐颗解帧时，某帧缺失/迟到也可能使后续有效舵机帧连续被错配。计数本身没有提供发送者是 ID 200、乱码或主动压线的证据。此前“三场风暴”的现象记录保留，因果定案撤回。

### 2026-10-25 追问：设备主动广播还是主控请求

- **结论**：当前舵机与 IMU 遥测采用主控请求、从站应答。Radxa 发读取请求，被点名的节点按协议顺序/时序回数据；正常协议行为不是各设备自由主动广播。IMU 板内持续采样、更新寄存器与向总线发送数据是两件事。
- **部署代码复核（本机只读）**：本轮经 SSH 读取 `~/servo-web/server.py` 的 `read_states_with_imu`，真机分支先 `BUS.sync_read(servo_ids, ...)`，收到应答或超时后再 `BUS.sync_read([200], ...)`（IMU 暂时出列时按既有策略 PING 探测）。函数旧 docstring 仍写“同一条 sync_read、200 排第一”，与执行代码不符，不能作为现行流程依据；此前 READ 晚答/100% 及时等注释也已由上节实测纠正。本轮未改部署程序。
- **广播含义**：SYNC_READ 请求本身可以用广播地址 `0xFE`，数据区列出要读取的 ID，由这些节点依次应答。广播的是主控发出的请求，不是节点自行定时上报。当前正常顺序为“主控请求 15 舵机 → 舵机依次应答 → 主控请求 IMU 200 → IMU 应答 → 下一轮”。
- **另一条链路**：同文件 `stream` 在读取完成后调用 `broadcast`，是服务端通过 WebSocket 向浏览器客户端推送结果，不是舵机物理总线上主动广播。
- **对故障的解释边界**：前述自然 CRC 错误应答表示 IMU 判定收到的请求校验失败，不能改述为“IMU 主动上报的数据在主控校验失败”。此结论仍不定位到某根线或具体固件缺陷。
- **依据与限制**：本地只读参考 `references/microduck-community-kit/firmware/v1/docs/imu_to_dxl_protocol.md:38–40` 明确从站只应答，§2 描述半双工请求/应答，§4 描述飞特 SYNC_READ；此前原始 JSONL 的 TX/RX 与本轮部署代码一致。再次打开上游 tag 对应 raw URL 时网页工具只返回空正文，未新增在线正文证据。没有停服、操作串口或新增硬件测试；仅补充研究，未 commit/push。

<a id="timeout-and-overlap-20261025"></a>

### 2026-10-25 追问：上一个请求没返回，主控会不会直接发下一条

**结论**：当前 servo-web 的正常读取路径按事务串行执行，会等应答或超时，不是发出请求就立即再发一条。但“主控已经超时”不表示“从机以后绝不会再答”；超时后的迟到应答仍可能与下一事务交叠。应区分软件串口锁、协议超时和实际电气总线是否空闲。

本轮只读提取 Radxa 当前部署的源码和调用点，保存为[等待/超时源码快照](./request-timeout-source-20261025.json)。`feetech.py` 和 `server.py` 哈希分别仍为 `f49d5926ba7a4f01e55ed2e32cc78797a92f084605790ffca18d35e937605c3d`、`67e91b7abb495adf2bfcc5ea38df163e137f92418d3a91dc43ce7e963f115c31`。以下行号为该快照的远端文件定位：

- `feetech.py:73–77` 初始化 `threading.Lock()` 为 `_io`；`ping/read/sync_read/write/sync_write` 的正常收发路径持有同一锁。该锁约束同一总线对象的调用线程，不是跨进程锁，也不能取消从机尚未发出的应答。
- `sync_read:199` 在锁内仅发送一次含 ID 列表的请求，然后逐个读取预期 ID 的应答，循环内不再发请求；读完或对应读操作报错后才释放锁。一次请求可对应多颗设备的应答。
- `server.py:1436` 的舵机读取调用返回后才读取 IMU；两次调用各自持锁，不是把两事务包在一个总锁里。`stream:1474` 使用 `await asyncio.to_thread(...)` 等本轮读取结束，没把未完成的读取任务按固定周期不断堆起来。`server.py:302` 构造 `FeetechBus(port, baud)`，沿用默认 `timeout=0.02`，本轮在该文件未发现直接绕过接口的 `BUS._send/BUS.ser/BUS._read_status` 调用。
- `_read_status:109` 虽设帧头截止时间 `timeout*3`（60 ms），但 `serial.read(1)` 首次空读就 `break`；因此完全无字节时可约 20 ms 结束。收到部分帧时还有后续 ID/长度和包体读取期限，不能把所有失败都写成恰好 20 ms。
- `_send:95` 发下一请求前清接收缓存，再提交新包；清缓存只能清已经到达的数据，不能阻止设备随后才发包。读取超时后未见专门的“持续静默直到确认总线空闲”恢复阶段。
- 广播 SYNC_WRITE 和显式 `write(wait=False)` 是不等待应答的独立路径，不应拿来概括读取行为；当前 `wait=False` 调用点位于改 ID 方法，未在本轮执行。

**可能的失序机制（推演，尚未实测捕获）**：主控向 A 发请求 → 等到超时 → 发给 B → A 此时才答。如果 A 的发送与主控/B 的发送重叠，可能发生电气冲突；即使没有同时发送，A 的有效迟到包也可能被当作 B 的应答，产生错 ID。互斥锁只能防止主控线程在同一对象上并发事务，无法消除这种跨事务迟到。

还有一种无需电气冲突的错配：多 ID SYNC_READ 按列表读取，但 `_read_status(expect_id)` 收到完整、校验通过的其他 ID 包时直接报错并消耗该包。若前面一个节点缺答，后面及时返回的有效包也可能连续被错配，形成多个 `bad_id`。因此 `sync_read` docstring 的“任何一颗超时不影响后面的”不是所有异常下都成立；也不能由 `bad_id` 反推 IMU 主动压线。

**与现有证据对照**：较早原始捕获和 18:13 配对实验都延长监听到约 100 ms 周期结束，缺答时没有接收到迟到字节；18:18 DXL 独立请求也在每次完整 100 ms 监听中捕获 CRC 错误，期间没有插入下一条请求。这削弱“主控约 20 ms 就发送下一条，撞上前一应答”作为所有现象的统一解释，但不能排除其他时段、超过监听窗口的迟到或从机侧未被主机接收到的信号。尚未抓到“上一事务迟到包撞下一事务”的原始波形，不能把这个机制写成当前故障根因。

### 2026-10-27 深夜续 2：两条独立 sync_read 的时序冲突分析（源码级）

用户判断：10-24 拆分补丁未解决问题、可能引入新问题、不是根因。逐行核对 `read_states_with_imu` + `feetech.py` 后确认：

**并行发送：不存在。** 全部总线操作在单线程顺序执行（`asyncio.to_thread` 一个工作线程），且每条指令持有实例级串口锁 `self._io`；页面手动操作同样被 `_io` 挡住。字节层面不可能两条指令同时驱动总线。

**先后发送：紧邻，存在四个具体时序风险点：**

- **R1 帧间空闲与板固件分帧判据同量级（当前最强候选）**：舵机 sync_read 最后一颗应答收完 → Python 层退出循环/释放锁/decode 15 颗状态/再进第二条 sync_read/`reset_input_buffer`/write 请求——间隔仅约 0.2–1ms（纯 Python+系统调用开销，带 GC/调度抖动）。同源 v1 固件的帧间隔判据 `BUS_GAP_US=500µs`（>500µs 才判"新帧"），出厂固件若有类似判据，**IMU 请求恰好落在分帧判据的临界区**：前一流量尾巴与本请求有时被分帧、有时粘连 → 概率性误组帧 → 不答。与三个观测同时吻合：①拔舵机后舵机 sync_read 整个跳过（`if servo_ids else {}`），IMU 请求前只剩上一拍自己的应答（间隔 ~100ms）→ 99.9% 完美；②丢包断续不成簇（Python 抖动决定每次粘/不粘）；③丢包率随接法梯度变化（紧邻流量的信号环境不同）。**注意**：探针 PING 的上一条流量也隔 ~100ms 一拍，却仍 7.4%——PING 丢不能只用 R1 解释，还叠加"单播慢路径"因素（10-24 注释实测 READ 单播常 >60ms 晚答/不答、sync_read 槽 0 应答 100% 及时，同日 10-25 17:43 链上分叉时单播又 100/100——路径差异与位置/负载两因素交织，都待分离）。
- **R2 迟到应答错入下一条（未触发）**：每条指令发送前 `reset_input_buffer()` 清缓冲。若上一条某应答在清缓冲**之后**到达，会被本条 `_read_status(200)` 当帧头消费 → expect 200 收到舵机帧 → bad_id+1 判 miss。观测 bad_id 全程 0，此路径未发生过，但机制存在。
- **R3 应答错位连锁消费（重要勘误：削弱上节"总线级瞬断"解读）**：`sync_read` 按请求列表顺序逐个 expect 读应答；`_read_status` 是**先消费整帧、再查 expect_id**。若中间某颗舵机丢答而下一颗照常应答，后者的帧会被当作"错 ID 帧"消费丢弃，随后全部错位 → **一轮内 15 颗连锁判丢**（注释"任何一颗超时不影响后面的"只在"超时等待"情形成立，错位情形不成立）。上节"3 秒内读不到"警告 7 次、每次 15 颗集体 ×1 的模式，**单颗丢答+连锁判丢即可解释，无需总线级瞬断**；13:39:17 的串口异常是另一机制。该解读降级"瞬断"为候选之一。
- **R4 丢答槽位空等 60ms**：`_read_status` 找帧头 deadline=timeout×3=60ms，丢答槽把整拍拖长（多颗丢可达数百 ms）——即 stream 注释"一次 sync_read 遇上掉包能占几百毫秒"的来源；也拉大后续 IMU 请求与前流量的间隔（R1 在"有丢答拍"反而缓解）。

**判别实验（一行级改动、可逆，直接命中 R1）**：把 IMU 的 sync_read 移到舵机 sync_read **之前**，或在两条之间插固定 5–10ms 延迟——丢包大幅下降 ⇒ "紧邻前流量"实锤（R1/固件分帧方向）；不变 ⇒ R1 出局，转向纯电气负载（E1）。结果与"拔舵机=完美"互为印证。

**kitbits 正确性核查（2026-10-27 深夜，应用户问）**：**改对了，三重证据**——①与 kit 官方位表逐位一致：`firmware/v1/host/bus.py:116` `TELEM_FLAG_BITS` 定义 0x01=sflp_valid、0x02=cnt_wrap、0x08=sensor_err、0x80=fusion_ok，kitbits 常量与之相同；②板②实采 12 秒 215 帧：`0x81`×213（bit0+bit7）期间四元数流动、sample_count 100Hz 连续递增——若 bit0 真是旧语义"未就绪"，这些帧不可能在正常出数；③`0x83`×2（0x81+bit1）出现频率精确匹配 100Hz × 8bit 计数的回绕周期（每 2.56s 一次）——旧语义 bit1="与 IMU 芯片通信失败"不可能每 2.56 秒规律性发生且数据照常流动，kit 语义 bit1=计数回绕精确解释。**限制**：bit2/3/4/5/6（陀螺饱和/传感器错误/模拟器/冻结/配置未落盘）在板②上从未置位出现过（bits 仅见 0x81/0x83），对应判定分支无实测验证；不置位时对判定零影响，仅真发生对应状态时影响提示文案。

**servo-web 线程模型核查（2026-10-27 深夜，应用户问）**：Web 数据处理/展现与总线读取**分层分开**，源码证据——①asyncio 事件循环（uvicorn 单线程）：HTTP/WS 收发、状态广播（stream）、IMU 帧广播（imu_stream 每 50ms，只读 `service.frame` 内存+µs 级锁）、日志推送，不碰串口；②asyncio 默认线程池：轮询 `await asyncio.to_thread(read_states_with_imu,…)`（server.py:1478）与页面命令 `await asyncio.to_thread(handle, cmd)`（:1550）都在工作线程执行全部串口 IO，线程间靠 `BUS._io` 串口锁串行化（同时刻仅一条线程碰串口；后到者在锁上排队——表现为操作偶发延迟，不是数据错误）；③独立 daemon 线程 `servo-web-monitor`（:1135）：每秒读 `MON["last"]`/`BUS.stats` 内存快照 + TIOCICOUNTER ioctl + 写 CSV（句柄常开、行缓冲、逐行 flush），不碰串口。交接点均有保护：`MON["last"]` 引用替换、`service.frame` 带锁、`LOG` 带 `_log_io` 锁。上一轮指出的日志问题发生在**总线工作线程内部的串口锁路径上**（trace→log 同步 open/write/close+print），与分层无关——且 monitor 线程的"独立线程+常开句柄+内存快照"正是异步总线日志 writer 可照抄的现成范本。
