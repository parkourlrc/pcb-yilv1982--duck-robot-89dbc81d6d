# Microduck 复刻项目 IMU 通讯故障与修复记录核查

日期：2026-10-26（北京时间）。范围：针对本机单口 jyg9 / community-kit GD32F303 IMU 的间歇缺答、有效请求被报 CRC 错，以及后来严重无应答，核查公开项目的第一方问题、提交、发布说明与实测记录。本轮仅联网调研、读本地材料和修订文档，没有连接设备、打开串口、停启服务、刷写或修改硬件。

## 结论

**有相似案例，而且当前单口板的同源项目明确记录过通讯缺陷及修复。最有价值的线索是回声过滤吞帧头、计时器回绕后静默、接收中断处理过慢丢字节，以及硬件上拉/串联电阻调整。** 但是前三项软件修复已存在于官方 `firmware-1.5.1` 标签源码中；本机也报 1.5.1，但此前构建指纹没有匹配官方包，不能只按版本号判断是否包含修复，更不能据此认定根因或直接升级。

**对现有排障计划的直接更正：官方 1.5.1 发布说明明确关闭调试串口打印，标签与当前源码的 CMake 均默认 `DBG_ENABLE=0`。** H1 引出日志 UART 不等于运行镜像会输出日志。先核对本机构建和日志配置；若已知关闭，跳过“等待 H1 日志”这条路径。不要把无日志判为 MCU 死机，也不为获取日志盲刷镜像。

本机完整既有证据见[IMU 主记录](../舵机网页工具惯性显示/research.md)与[调试计划](../舵机网页工具惯性显示/debug-plan-20261026.md)。本文所有其他作者的成功率、板卡故障和修复结果均为**上游自述实测**，没有在本机复现。

## 同源 GD32 项目的具体案例

### 1. 回声过滤吃掉下一个请求的帧头

- **来源/定位**：jyg9 `bus_timing_borrow_plan.md` §4.6.1，记录日期 2026-09-25；[固定提交原文](https://github.com/jyg9/microduck-community-kit/blob/35a4bf8a4c7c7038ab7b20f0aa86236101a4d596/firmware/v1/docs/bus_timing_borrow_plan.md#461-echo_skip-吃掉下一帧帧头-srcuart_portc)，[本地快照](sources/jyg9--firmware--v1--docs--bus_timing_borrow_plan.md)。
- **上游症状**：每两次请求只答一次；200 次请求的字节都到 UART，只有 100 次组成有效帧。把请求间隔拉到 20 ms 也存在。
- **上游根因与修复**：发送后固定丢 2 字节的 `echo_skip` 假定板上存在发送回声；实际板没有回声，剩余计数吞掉下一请求的 `FF FF`。改为以发送结束时间为锚的短回声窗口，1 Mbps 下约 30 µs。
- **上游验证**：修改后 400/400 应答，`rx=3200 / frames=400 / answered=400 / echo=0`。
- **本机适用性**：同源板、请求到了却无回包、拉间隔无效，有较强机制相似性；本机不是固定隔次失败，且官方 1.5.1 已含修复，不能直接定为此 bug。

### 2. 计时器回绕后，IMU 在运行中途完全静默

- **来源/定位**：同文 §4.6.2，2026-09-25。
- **上游症状**：传感器仍健康，通讯中途静默；有效帧/应答计数冻结，`echo` 随收到的每个字节上涨。也曾表现为 robotd 首次同步读取缺 ID 200。
- **上游根因与修复**：120 MHz 的 32 位 DWT 周期计数约每 35.8 秒回绕，直接除成微秒破坏期限比较，导致正常接收被当作回声。改用 SysTick 毫秒基准加锁存的亚毫秒周期差，形成正确的微秒计时。
- **上游验证**：重流量下 `echo=0`，异常的超大 `loop_max` 恢复正常，robotd 首次绑定成功。
- **本机适用性**：与“之前能出数，后来长时间不答”相似；**本机未确认有 35.8 秒周期**。官方 1.5.1 已包含修复，需要先匹配本机二进制来源。

### 3. CRC 运算拖长中断，紧随其后的字节被覆盖

- **来源/定位**：同文 §7.8；[提交 42f8bfa](https://github.com/jyg9/microduck-community-kit/commit/42f8bfa0badb)，2026-09-30；[提交证据](commit-42f8bfa0badb.json)。
- **上游症状**：Fast Sync Read 中间位置不应答，节点 `rx_bytes` 比主机发送少 1 字节，但 `rx_errors` 始终为 0。
- **上游根因与修复**：逐位 CRC16 在 UART 接收中断内耗时超过 1 Mbps 的一个字节时间；随后接收字节被覆盖。改为 256 项查表 CRC16，降低中断耗时；修复后接收字节数逐字节吻合，中间位置测试通过。
- **本机适用性**：证实同源固件曾出现“接收丢字但错误计数为 0”。不过该案例主要在紧随流量/聚合帧中暴露，**不自动解释本机稀疏单播 PING 的错误 CRC**。本机读到的是主控 UART 计数，上游这里是从机 UART 计数，也不能当成同一测量点。

### 4. 硬件电阻修改，作者明确写了偶发丢包

- **来源/定位**：[提交 1d910b5](https://github.com/jyg9/microduck-community-kit/commit/1d910b5a82c6)，2026-09-30；[提交及差异](commit-1d910b5a82c6.json)。作者将其描述为飞特上拉电阻过小导致的小概率丢包优化。
- **可复核变化**：提交 BOM 中 **R31 从 10 kΩ 改为 100 kΩ，R5 从 100 Ω 改为 51 Ω**。本地只读 PCB 显示 R31 接 `/DATA1` 与 `+3.3V`，R5 接 `/DATA1` 与 `Net-(D2-Pad2)`，即上拉及信号串联路径；[提取结果](local-resistor-check.json)。不能把两颗都叫上拉。
- **证据等级**：作者修复声明 + 实际设计/BOM 变更；该提交没有提供可对照的前后丢包率/波形，不视作已经完成量化因果验证。
- **本机适用性**：值得先确认成品批次是否包含此改动。**仓库现存只读副本已经是 R31=100 kΩ、R5=51 Ω，不能由此推断实物阻值。** PCB 日期/外形不能代替 BOM 与实物匹配，不在本轮发出换阻或短接指令。

### 5. 调试日志让数据每 2 秒冻结约 53 ms

- **来源/定位**：[提交 0456a83](https://github.com/jyg9/microduck-community-kit/commit/0456a83e863db7d8faf50c1a593397f719d3ab49)，2026-10-02；[发布说明](https://github.com/jyg9/microduck-community-kit/releases/tag/firmware-1.5.1)；[提交](commit-0456a83e863d.json)、[发布快照](jyg9-releases.json)。
- **上游原因**：每 2 秒的状态打印阻塞主循环约 53 ms，采样不发布，主机读到重复姿态。关闭日志并修复 `DBG_ENABLE=0` 的编译问题，发布 1.5.1。
- **上游验证**：2 秒周期冻结消失，采样计数重复从 1.72% 到 0/7394；robotd stale 从约 2.1% 到 0.273%，并非所有 stale 都消失。
- **本机适用性**：可以解释数据旧，不足以单独解释本机正确请求 CRC 错和长窗完全无字节。它对**H1 是否有日志**的影响更直接：标准 1.5.1 默认没有这些打印。

### 6. 主机截断应答、USB 接收遗漏，不能直接判从机坏

- **来源/定位**：时序文档 §7.7、提交 `1babe97c4d6a` / `08999a430d6d`（2026-10-02），以及 [e0b3058](https://github.com/jyg9/microduck-community-kit/commit/e0b3058e4f4e)（2026-09-30）；[提交列表](community-commits.json)、[独立计数对照](commit-e0b3058e4f4e.json)。
- **上游处理**：Radxa ttyS2 每笔 `tcdrain/flush` 曾额外消耗约 12 ms，删除后控制环从 36.3 到 50 Hz；接收突发的空闲截止从 2 ms 放宽至 4 ms，留出尾部余量。另有 50 发中主机少收 1 发、节点却 `frames/answered +50` 且 TX 字节齐全的记录，提示先对应从机计数。
- **本机适用性**：用于辨别“没发”与“主机没收到”，不是通用增加重试就算修复。本机已存在独占长窗无字节及请求 CRC 错，不能用主机截断解释全部现象；微雪全无字节也不同于偶发少收一帧。
- **上游文档冲突**：协议文档 §12.8 仍将一组旧尾部缺失概括成 USB 整块丢包；较具体的时序文档 §7.7 已补 10-02 的主机处理修复。本文采用后者的修复说明，保留 e0b3058 的独立从机计数证据；不将推断写成 USB 物理层已经定罪。

## 版本核查与建议次序

1. **先确认成品板实际版本与构建来源。** 向供板者核对：是否含 9-30 的 R31/R5 调整；本机 `1.5.1 / slot A / 0xD9CA0DEF` 对应哪个源码提交及编译选项，`DBG_ENABLE` 是 0 还是 1。本轮没有代发消息。
2. **历史固件 bug 是核对清单，不是刷新理由。** 本轮直接读取 `firmware-1.5.1` 标签下 `uart_port.c`、`us_time.c`、`crc16.c`、`CMakeLists.txt`，确认时间窗回声过滤、SysTick 锁存计时、CRC 查表以及默认关日志均存在；[标签核查与哈希](firmware-1.5.1-check.json)。如果本机确实已包含这些实现，应降低旧 bug 的排查优先级，而不是重复修已经修过的代码。
3. **H1 监听改为条件路径。** 已确认日志关闭则跳过；构建仍未知、接线已核对时可短时被动监听，但无输出不诊断 MCU 坏。若确有日志，着重对照 `rx / echo / frames / answered / tx` 与主机漏答，不继续重复大矩阵扫描。当前源码的统计行不直接输出全部错误细项，限制见既有[调试计划](../舵机网页工具惯性显示/debug-plan-20261026.md)。
4. **不直接刷 1.6.0。** 2026-10-09 发布明确叫 FT6 特殊版本，飞特侧与 native 1.5.x 契约不同，不能当普通修复升级。上游 #2 在 10-16 的兼容回复主要针对 XL330/DXL 路线，不能覆盖本机飞特状态位和安装补偿。来源：[发布快照](jyg9-releases.json)、[#2 回复](community-comments-2.json)。

**可供用户转述的核对文字（未发送）**：我的单口 GD32 IMU 在 HAT 上单独 PING/READ 也间歇无回包，正确 DXL2 请求曾返回 CRC 错；固件身份 1.5.1、槽 A、镜像 CRC32 0xD9CA0DEF。请确认对应源码提交、日志开关，以及该批次是否已经采用 R31=100 kΩ、R5=51 Ω 的 9 月 30 日修订。当前没有证据认定板坏，也未刷 FT6。
