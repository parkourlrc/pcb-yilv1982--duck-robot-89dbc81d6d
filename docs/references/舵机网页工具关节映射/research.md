## 问题与范围

用户反馈：`servo-web` 里有的关节方向是反的，怀疑页面用的舵机数据不是本机真机的。

## 结论（先说结果）

1. **实时读数本身来自本机真机**：`PROGRESS.md` 2026-10-22 记录板上以 `--port /dev/ttyS2` 启动，15/15 在线、总线 7.1 V、超时/校验错 0；页面顶栏此时显示“串口 /dev/ttyS2”，`/api/info` 的 `fake:false`。若显示“模拟：没连串口”，才是虚拟舵机。
2. **“哪个 ID 是哪个关节、正方向是哪边”这一层不是本机的**：上游 0.15.2 的关节表是 `20–24=左腿、10–14=右腿`，与本机 2026-10-17 定案（`10–14=左腿、20–24=右腿`）**左右整组相反**。腿的 10 颗会画到模型的另一条腿上；左右镜像轴的关节（髋 yaw/roll、踝等）看起来就是“方向反了”。
3. **方向表 `directions.json` 是上游那台机器的记录**：15 颗全 `-1`，注释写明 2026-09-20 实机逐颗核对；不是本机逐关节验收结果。本机中位校准后零位与上游不同，装配齿位也可能不同，不能直接当作本机方向。
4. **内置姿态也是上游的**：`poses/站-2026-09-20.json`、`poses/缩-2026-09-20.json` 是上游 2026-09-20 的原始读数，关节名按上游左右分组，零点也绑定上游校准。把它们发到本机不等于本机姿态。
5. **官方姿势/一键校准会按上游左右算目标**：`OFFICIAL_FOLD`、`DEFAULT_POSITION`、官方站/坐/折叠都按 `20–24=左腿` 换算。映射未修正前使用，左右腿目标会互换，镜像关节可能被反向驱动，属带载动作风险。页面每颗的 `±` 只改显示方向，**不能**修正“20 号被当成左腿”这个映射错误。

## 为什么表现是“有的关节反”而不是全部乱

- ID 20–24 在本机是右腿，模型里却是左腿：动右腿舵机，3D 动的是左腿。左右腿的局部坐标互为镜像，同号角度在两侧世界方向相反；髋 yaw/roll、踝等镜像轴关节看起来就是方向反。
- 髋 pitch、膝等以同一根横向轴弯的关节，反向不一定一眼看出，所以体感是“有的反、有的好像正常”。
- 头颈 30/31 后来也确认与上游相反（实物 30=head_pitch、31=neck_pitch，2026-10-22 用户确认）；30–34 的 dirs 全 `-1`，已由用户在 3D 与实物对照中确认。

### CAL 的语义：改零点，不是驱动到 2048（2026-10-23 用户追问）

用户问“点 CAL 为啥不是位置设置成 2048”。代码 `calibrate_one` 的语义是：

- 用 0x0B 把**当前物理位置**标成 2048（改偏移），而不是把关节驱动到 2048；
- 关扭矩窗口里关节若被重力带下去，代码补偿偏移后**把目标写成当前读数**，让关节停在垂下的位置，避免恢复扭矩时突然拉回；
- 因此大下垂时，CAL 完成后读数不是 2048，3D 仍显示垂下的角度；要回到 2048 得另外点“回零位”。

2026-10-23 00:53–00:54 用户连续点了 20/21/22 的 CAL，日志显示每次关扭矩关节都大幅下垂：

- 22：00:38 pre 1636→1224（下垂 -824）；00:54:05 pre 1233→418（下垂 -1630），偏移 541→1356；当前 22=424。
- 21：00:54 两次 CAL，当前 21=1267；20 也在 00:53:57 校过一次。
- 备份依次为 `calib/eeprom-20261023-003818456.json`（22 原 offset 129）、`...005357966`（20）、`...005400228`（21）、`...005405882`（22）、`...005409246`（21）。

**结论**：CAL 没有坏，但它在无支撑的髋 pitch 上不可用；连续点只会让腿越掉越低、零点越偏。恢复应托住右腿，按“撤销上一次”的顺序逐条撤销（21→22→21→20→22），再把腿摆回直腿零位；22 可临时用软件零位（后来为 CAL 测试已清空，见下），21/20 恢复原偏移后按 2048 核对。若希望 CAL 完成后自动走到 2048，需要另加“校准后回 2048”的可选步骤，不能在无支撑时默认做。

**进一步根因（2026-10-23 用户追问）**：CAL 的定义确实是“当前物理位置 = 2048”，但 #22 这次没有做到，属于 CAL 的边界缺陷，不是用户理解错：

- 00:54:05 的 0x0B 把偏移从 541 写到 1356，读数反而从 1233 掉到 418；也就是说偏移被写反/写错方向。
- 两次 CAL 的数字完全符合 `新位置 = 2×旧位置 − 目标`：
  - 00:38：pre 1636、target 2048 → `2×1636−2048 = 1224`（日志 final 1224）；
  - 00:54：pre 1233、target 2048 → `2×1233−2048 = 418`（日志 final 418）。
  偏移变化量正好是 `target − pre`（+412、+815），说明 **HD-1910 固件 3.46 的 0x0B 内部按“读数 = 原始 + 偏移”算，而位置反馈实际是“读数 = 原始 − 偏移”**。0x0B 把偏移加到了反方向，位置因此变成 2×旧位置−目标。
- `偏移符号探针 #22 偏移 +1 读数没变`，1 步太小/没落到反馈分辨率，符号没探出来；`calibrate_one` 的判据只看“偏移变了没有”，没有回读 `pos == 2048`，所以把这次错误当成功。
- 叠加关扭矩后 -1630 步的下垂，最终既不 2048、也不是你摆的直腿姿态。
