优先排查两类：**IMU 支路电源/接触及物理收发异常**、**从机 UART 接收/回声抑制/组帧异常**。主机显示/混读解析单独作为根因的解释力较弱；IMU 传感器采样自身故障也难单独解释 PING 请求 CRC 错误，但仍通过采样日志检查。此为调试优先级，不是概率或定论。

### 1. 先确认日志配置，启用时再用 H1 被动读取

官方 1.5.1 默认关闭日志是为修复每 2 秒打印阻塞主循环约 53 ms 的问题；只看 `main.c` 有统计打印不能证明成品镜像包含它。本机固件指纹尚未匹配，优先从构建资料或供板者确认开关；已确认关闭则跳过本节，不为看日志直接重刷。若开关仍未知、接线已经核对，可短时被动监听，但空输出不能证明 MCU 故障。

**准备**：根据现有 PCB 文件、用户实物正反面和适配器型号确认 H1 的位置、针序及真实 3.3V RX 电平。实物与本地设计修订未逐项匹配前，不按纸面编号直接焊接；如需焊线，在断电状态完成。H1/H2/H3 不能混用，详见[接口核对](../惯性单元三版来源对比/research.md#usb-debug-20261026)。

用户表示不确定 H1 位置，已用 10-14 原图生成并查看[H1 定位图](../../photos/archive/imu-gd32-single-port-20261014/imu-single-port-h1-location-20261026.png)：元件面朝向观察者、白色 3P 座朝右时，H1 在左下安装孔上方、金属晶振左侧，为竖排四焊盘。该图仅定位接口，没有标照片上下针序；当前焊接情况尚未确认，需要 H1 局部近照再核对 TX/GND。

首次仅监听，以下为**逻辑网络关系，不是实物数针图**：

| 单口 IMU | FT232H | 说明 |
|---|---|---|
| H1 DEBUG_TX（设计 pad 4，PB6 经 R11） | D1 / RX | 只接收 IMU 日志，不接 3P 总线 DATA |
| H1 GND（设计 pad 2） | Gnd | 共地 |
| H1 DEBUG_RX、3.3V | 不接 | FT232H D0/TX、3V/5V、RTS/DTR 等其他线均不接 |

IMU 继续用已确认的 HAT 电源；电脑 USB 只给适配器供电。不使用 H3 USB 下载口，不改变启动跳线。现有照片能辨认 H1 区域，但不能据此宣称当前焊接、针序/修订已完成现场核对；不拿松动探针临时顶在带电焊盘上。

满足上述条件时，以公开源码日志串口配置的 **115200、8N1、无流控**读取 30–60 秒，保留原始字节和接收时间，同步保存 servo-web 日志。此波特率不表示默认启用日志。HAT 原有总线程序继续独占，不另开 ttyS2。开始捕获后记录连接事件和已知人工断电，不能把准备接线产生的启动横幅当自然复位。既有 `tools/serial-log.py` 默认 1.5 Mbps 且解码后写文本，不能直接把它的输出叫原始字节证据；正式采集须显式设 115200，并另存原始 bytes/hex，乱码不经替换后再作协议判断。

应观察：运行时间 `t` 是否持续、`samples` 是否增长；`sensor/present/qvalid`；配置 ID/波特率/协议锁；**uart1** 的 `rx/tx/dropped/err/echo/frames/answered`，以及 `lost/gaps/ignored`。uart0 是调试口，不与 uart1 总线计数混淆。如果实际日志格式不同，按实际版本建立字段解释。

**边界**：本地 `main.c:143–175` 确实打印上述字段；`bus_stats_t` 有 `bad_crc`，但默认 `stats_print` **没有直接打印 bad_crc**。不能许诺串口日志一定给出逐字节请求或每次 CRC 原因；本地 `uart_port.c` 的 `err` 主要计 ORERR 溢出，并非所有模拟信号/帧错误的全集。字段与计数解释见[源码快照](./imu-diagnostic-observability-20261026.json)。

**若无日志**：只检查 H1/接收器/地/波特率和本机日志是否关闭，不据此判 MCU 死机，也不为开日志直接刷机。没有可用日志时进入硬件观测或有限单变量替换分支。

### 2. 只在取得日志后，做一轮能对应到从机计数的短请求

先看被动日志是否已揭示持续复位等明确分支；有明确分支就跳过不相关实验。若仍需分辨接收/应答阶段，安排一个不发动作的短窗口：记录服务/扭矩当前状态，避免与用户动作同时进行，暂停现有串口持有者后由一个诊断进程独占。结束恢复测试前的应用状态，不自动开启其他查看器、重启板子或改变扭矩。

保持接线和电源不变、线路 1 Mbps 不变，从**单个 ID 200 PING**开始：约 1Hz 10 次，若仍有区分价值再约 10Hz 20 次。每次完整监听至少 100ms，保存主机 TX/RX 和 H1 同期计数；请求频率与串口波特率是两个不同变量，不同时改变。只有 PING 稳定而读取异常时，才增加一种 READ；不再重复之前六组混读大矩阵。

若需要利用 `0x20` 区分静默丢弃，可再用少量正确 DXL2 PING。切协议前确保总线至少 300ms 无其他请求，并检查实际固件协议锁；不写协议锁、不发送人为坏 CRC、不把切换粘滞期误当硬件丢包。先前已经取得 CRC 错误证据，本轮不以再次复现它作为所有分支的强制门槛。

主机与 H1 以本机单调时间/UTC对齐，并利用稀疏请求窗口关联；USB 日志时间不当作微秒级物理时间。初次不打开逐字节 TRACE，避免改变接收时序。记录计数增量而非只看累计总值；共线其他节点与自身回声也可能增加 rx，不能直接把 rx 当“收到的本节点请求数”。

### 3. 根据观察结果选择一条后续路径

| 同步观察 | 下一项区分实验 | 能定位到哪里 |
|---|---|---|
| 没有人工断电却重复启动、运行时间清零 | 同时观察 IMU 入口和板内 3.3V、复位原因；若有压降，固定电源与线束逐项 A/B/A | 压降先于复位支持供电；电压稳定仍复位则查看门狗/异常/复位脚，不能看到复位就断言电源坏 |
| MCU/采样持续，独占请求窗口 `uart1 rx` 无相应增长 | 核对日志中实际 ID/波特率/端口，再观察 HAT DATA、IMU 接头 DATA 与 MCU RX | 请求可能没有到达有效接收通路，也可能 UART 配置/统计本身不符；用信号证据区分 |
| rx 增长，frames/answered 不相应增长，或 err/echo/gaps 异常增长 | 对比 MCU RX 脚实际收到的字节与主机 TX；检查 UART 溢出、回声屏蔽、字节间隔及协议解析 | MCU 脚前已变形/丢字节→物理链路；输入正确但固件丢帧→固件接收路径嫌疑增强，需对应构建确认 |
| frames/answered/tx 增长但主机无字节 | 观察 MCU TX、半双工使能与总线回包，再追到 HAT RX | 统计只能说明尝试/排队发送；MCU 发出但总线没出→板上发送/方向；总线有而主机无→返回路径/主机接收 |
| PING 一直正常，传感器采样/四元数冻结或特定 READ 异常 | 查 SPI/IMU 状态与寄存器/固件布局，保持电气链不变 | 转向传感器或读取契约问题，而不是继续把所有缺答都归给总线 |

**设备限制**：目前确认 FT232H 与 DAPLink。FT232H 在本方案中只读 UART 日志，DAPLink 用作 SWD 后备；二者都不能直接替代示波器证明幅度、振铃、短脉冲或电源瞬态，也不能把 FT232H 的 GPIO 功能当作已经验证的 1 Mbps 总线分析仪。在接线点确认并具备合适工具时才执行波形分支，不要求现在带电拿表笔碰密集针脚。万用表正常值只能记录直流，不能排除瞬态。

旧换线/换位建议已被 10-27 多位置对照更新，不再优先重复；只有某条线出现明确接触异常时，才使用已知正常、针序相同的线缆/接头做一次单变量对照；端口互换不能顺带移动未知电源入口或切断舵机电源。每次都记录 H1 uptime，区别“换线改善”与“断电重启暂时改善”。仅某次重插后恢复属于线索，不足以定案；若不能安全保留其他条件，不强做该对照。

### 4. 只在定位证据指向后处理固件或板件

- 固件路径：先取得本机对应构建来源/日志身份，与可复现的接收异常对应。公开源码曾讨论回声屏蔽吞帧头、500μs 字节间隔等机制，只是核对点，不能在未匹配本机二进制前当作已命中缺陷。必要时再制定最小诊断固件方案、保留原镜像和恢复路径；本轮不刷 1.6.0、不盲目升级。
- 硬件路径：有某条电源轨/接头/收发节点的异常证据，再维修/换线/换板；不先采购配电改造。微雪问题暂作为独立支线，只有它能读已知正常舵机后，才重新用来交叉验证 IMU。
- 验证应回到故障原条件：修复前能复现，单项修改后失败消失或显著下降，再恢复原条件可重现（适合且安全时）。复测单读和正常舵机查询场景，分开统计零字节、错误应答、坏校验、迟到和复位；不是仅看页面连续亮。建议每条件至少 1000 请求并覆盖先前故障时间尺度；零失败只描述该窗口，不承诺长期绝对可靠。
