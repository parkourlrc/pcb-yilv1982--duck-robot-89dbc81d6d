# IMU 固件与 robotd 发送、等待、收发切换联合分析

日期：2026-11-01。用户要求沿发送／等待时序分析两端代码。本轮分析当前 v0.3 板所用 replica 0.2.0 STM32 固件、Radxa 的 `control.47+duck-v03.1` robotd 及其 serialport 4.9.0、板侧 pySerial 3.5／servo-web。未改生产代码、固件或服务，未打开串口、未追加动作；SSH 仅导入并读取 pySerial 源码。

**[推断] 时序仍是需要检查的方向，但必须区分主机等待上限、IMU 协议调度、实际 UART 发送完成和收发电路回切。** 已确认的原始坏帧不能排除软件改变发送节奏后触发的链路问题；此前“完整坏帧早到”只降低“正确应答来得太晚”的解释，不能排除全部时序原因。当前尚未从代码或实验找到能解释四次动作坏帧的确定根因。

## 1. 两端各自的计时器在计什么

下面的固件时限是归档 **0.2.0 源码常量**，不是本轮测得的线上时间。

| 所在层 | 时间 | 计时起点与作用 | 到期／触发后的行为 |
|---|---:|---|---|
| robotd 串口库 | ≤2 ms | 一次 `ppoll` 等待可读／可写；有事件立即返回 | 向上返回 TimedOut，遥测循环继续等剩余总预算 |
| robotd 遥测 | 20 ms | `imu_to_dxl_telemetry` 开始时；覆盖两段发送、接收、解析与线程调度耗时 | 返回失败；起身阶段取消并卸力 |
| robotd 广播写 | 4 ms | 本次 `send()` 调用预算 | 约束写入内核队列的等待；不是物理发送完成或动作完成确认 |
| robotd 控制整组回读 | 10 ms | 15 颗 40/1 或 42/2 控制回读开始 | 不完整则失败；这是额外事务，不包含在前一轮遥测的 20 ms 内 |
| servo-web／pySerial | 每次 read 20 ms | 每次底层 `read(size)` 重新建 Timeout；循环收满 size 或超时 | 返回收到的部分字节；上层据长度／校验判错 |
| servo-web 帧头循环 | 名义 60 ms | `_read_status()` 开始找 `FF FF` | 但任一次 `read(1)` 空读就提前退出，不保证等满 60 ms |
| IMU 请求解析 | 500 µs | 两个接收字节的时间戳差，比较为 `>` | 丢弃半包、增加 `receive_timeouts` |
| IMU 应答调度 | 50 µs | 收到并接受完整请求的最后字节时间戳 +50 | 到点且条件满足才调用发送 |
| IMU 应答失效 | 2000 µs | 从上述“应答应发时刻”再计；比较为 `>` | `cancel_reply`，不发送旧应答 |
| IMU UART 发送 | 21 字节时 1210 µs | 本地进入发送循环；`len ×10 bit /1 Mbps +1000 µs` | 发送等待超时、释放驱动并计 `tx_timeouts` |
| IMU SYNC_READ 排队 | 1 ms 空槽、25 ms 整笔 | 仅当 SYNC_READ 列表包含 200 且它排在别人后面 | 跳过未答槽／取消排队；**当前单播读取不使用这条路径** |

源定位：[源码摘录与 SHA](imu-robotd-timing-sources-20261101.json)；固件 `Core/Inc/protocol.h:24–28`、`board.c:246–264`；robotd 固定源 `feetech.rs:173–180, 693–751`；部署补丁 `imu_to_dxl_telemetry`；串口库 `tty.rs:466–504, 732–735`、`poll.rs:14–65`。

**关键区别：[源码核验] `set_timeout` 只有 `self.timeout = timeout`，没有 `tcsetattr`、清缓冲、GPIO 操作或发送。** `TTYPort::read` 调 `ppoll(POLLIN, timeout)`，就绪后 `read` 一次；返回多少字节便喂多少给持续存在的 Decoder。下一次 2 ms 等待不会清空已经收下的半包，也不会重发 READ。这里不是“每 2 ms 才采样一次串口”，没有把 UART 比特采样频率改低。

## 2. 当前单播事务的完整代码路径

### robotd 发起请求

1. control 循环先调用 `telemetry`；两段严格顺序执行，成功后才推进 `step_hold`。
2. `send()` 先 `clear(Input)`，落到 `tcflush(TCIFLUSH)`，丢弃此前未消费的输入。随后等待 fd 可写并将整包写入内核，短写时继续写剩余部分。
3. `write()` 成功意味着字节被内核接收。当前没有调用 `flush()/tcdrain()`，没有等待物理 UART `TC` 的用户态接口，也没有发包后的固定静默时间。HAT 的方向由硬件自动处理，robotd 不用 GPIO／RTS 在读写之间手动切方向。
4. IMU 请求固定为 `FF FF C8 04 02 38 0F EA`，8 字节。紧接着启动可读等待；“提前等接收”本身不会驱动 DATA，更不会强制 IMU 立即响应。
5. 合格 IMU 包收齐后进入舵机 SYNC_READ；严格完整反馈收齐才执行本周期目标写。坏帧被 Decoder 丢弃，当前错误返回路径最后笼统写为 `response timeout`。

原顺序、改序仅改变第 5 步两段的位置。它们没有改变 UART 排空、包间隔、控制频率或固件 50 µs 回答条件，所以“改序仍失败”不能当成全部时序已排除。

### IMU 接到请求并应答

1. USART2 IRQ 将每个接收字节及 `board_micros()` 时间戳放入 256 项 ring；主循环逐字节 `proto_feed`。
2. `scan` 根据帧长收完整包并校验；READ 必须是发给 200、参数恰为地址和长度。`build_read` 获取快照、填 15 字节数据，再 `make_status` 算 checksum。
3. `schedule` 设 `pending=READY`，`reply_due_us=最后接收时间戳+50`。主循环接收处理结束后才 `proto_poll`。如果主循环此前因其他工作晚了，50 µs 不会从处理结束时重新开始计。
4. READY 期间只要 `proto_feed` 又得到一个字节，就取消旧应答；并不要求新字节构成有效命令。`proto_poll` 晚过到期时刻 2000 µs，或仍有半包，也会取消。
5. `board_bus_send` 先进入全局 IRQ 临界区并关闭 USART2 IRQ，再检查 ring、UART BUSY、未取走字节和错误标志；不空闲则 `tx_busy_drops` 增加、恢复 IRQ 并拒发。通过后拉低 PA1 使能驱动、退出全局临界区并发送；USART2 IRQ 在发送期间仍关闭。
6. 每字节等 TXE 再写 TDR，全部写入后等 **TC** 才拉高 PA1 释放总线。发送后清 RX 和错误标志、恢复接收 IRQ。没有在写入最后一个 TDR 后立即释放驱动。

**[源码核验] 当前只读舵机的 SYNC_READ 列表没有 200。** 固件 `sync_read()` 搜索不到自己就返回，既不建应答也不进 `WAIT_TURN`；广播 SYNC_WRITE 分支忽略内容。因此不能把“1 ms 排队槽／25 ms 排队超时”套到当前 ID200 单播 READ。源码定位为 `protocol.c:155–190, 255–263, 288–294, 352–412`、`board.c:196–267`。

## 3. 实际包长与软件时序边界

**[计算，假设 1 Mbps、8N1、UART 连续发送且没有排队／字节空隙]** 每字节 10 µs：8 字节 IMU 请求约 80 µs，21 字节应答约 210 µs；加源码设定 50 µs 应答延迟，理想请求起点至应答末尾约 **340 µs**。113 字节目标包约 1.13 ms。这些计算不是 strace 或示波器测得的物理耗时。

`read()` 较早返回不能说明请求本身在哪一时刻离开 UART；`write()` 返回也不能拿来当作最后停止位。但既有四次失败的“上一目标 write 返回至 IMU 请求 write 起点”分别为 **13.433、12.395、13.087、18.645 ms**，并非在主机调用层紧贴上一目标写。改序时最后约 5 ms 中还有完整的舵机反馈事务。故当前没有证据把这四次坏帧直接解释为“113 字节目标还没发完，主机又发 IMU 请求”。异常驱动排队或线上其他设备行为仍需测量，不能仅靠上述计算排除。

**[源码核验] 控制节拍不是包间静默保障。** `control_ticker` 使用 Tokio `MissedTickBehavior::Skip`，commissioning 启动时做一次 `reset_after(period)`；稳态按节拍调度，不在每笔 UART 发送完成后重新等一个周期。遥测之后的目标写、扭矩及回读还会占时间。若某周期超时或调度拖延，代码未另设“上一笔发完后最少空闲 X µs”的条件。这是需要区分的时序边界，尚不是四次坏帧的已知触发原因。

## 4. 与 servo-web 真正不同及相同的地方

| 项目 | servo-web | robotd | 对当前归因的含义 |
|---|---|---|---|
| 可读等待 | pySerial `select` 循环收满所需字节 | serialport `ppoll` 就绪后交付一块字节，Decoder 累积 | 分块粒度不同，但都可立即唤醒；不能将 2 ms 当固定轮询间隔 |
| 写入内核 | `os.write` 后还会 `select` 等可写 | 写前 `ppoll(POLLOUT)`，随后 `write` | 调用顺序和开销不同，二者均不等价于等待 TX 排空 |
| 发送后等待物理完成 | 未调用 pySerial `flush` | 未调用 SerialPort `flush` | 两边都没有显式 `tcdrain`，不是 robotd 独有缺项 |
| 发包前清输入 | `reset_input_buffer` | `clear(Input)` | 都可能抛弃旧残留；当前失败请求到读出坏包之间没有清输入调用 |
| 正常轮询 | 默认 10 Hz，舵机后 IMU | 约 50 Hz，原版 IMU 后舵机 | 完整发包节奏未因一次换序变成相同 |
| 错误处理 | 此次读取报错、外围记录缺失 | 坏帧后等到总截止、起身即卸力 | 改等待参数可能改变失败表现，不能自动改好坏字节 |

板侧源码读取确认 pySerial 为 **3.5**，来源 `/usr/lib/python3/dist-packages/serial/serialposix.py`，路径与 SHA 已在 JSON 中记录并核对。读取源码只导入模块，不实例化 Serial，不打开设备。pySerial `flush` 确实调用 `tcdrain`，但 servo-web `_send` 没有调用它；不要把库“提供 flush”误写成应用“已经等待发送完”。

## 5. 既有失败窗口与固件取消路径对照

重新按原始 strace 行复核四次新实验，每次在“IMU 请求至原生卸力前”均只有 **1 次串口 write（就是 READ 请求）、1 次 read（21 字节）**，其余是等待超时；请求到读出坏帧之间 **0 次 ioctl 清缓冲／重配**。原始请求后整个 `read()` 已返回的时间分别为 **0.972、1.628、1.050、0.728 ms**，这比上一轮列的 read 起点更严格；相关 6–8 次 ppoll Timeout 都发生在坏包已取得之后。

**[实测／推断]** 对这四次，2 ms 等待没有导致主机在半包时重发、切换方向或清掉正在读取的帧。IMU 前后 `cancelled_replies / receive_timeouts / tx_busy_drops / tx_timeouts` 都没有增量，因此这些已知“放弃不回包”分支不符合四次坏包的直接表征。它们可以解释其他窗口的无应答，不能把两种现象混为同一根因。发送期间 IRQ 关闭及清标志的局限见[研究记录](research.md)。

使用只读参考库原样 `protocol.c + control_table.c + Tests/bus_sim_shim.c` 编译临时本地共享库，在 WSL 中执行 [28 个确定性场景](imu-protocol-timing-simulation-20261101.json)，脚本为 [analyze-imu-protocol-timing-20261101.py](analyze-imu-protocol-timing-20261101.py)。输出放系统临时目录，参考库未写入。

| 注入的虚拟条件 | 原代码实际结果 |
|---|---|
| 完整 READ 后 49 µs 首次 poll | 继续 READY，尚未应答 |
| 后 50／500／2000／2050 µs 首次 poll | 发送 21 字节、校验有效 |
| 后 2051 µs 首次 poll | 取消，应答数 0，`cancelled_replies=1` |
| 请求中某字节间隔 499／500 µs | 完整应答有效 |

**限制：这是协议逻辑实验，不是真机时序复现。** 虚拟字节时间和传感器快照是人工输入，未运行 `board.c`、真实 ISR／USART、HAT、Linux UART 或电气线路；不能拿“28 个场景符合代码”排除板级发送／回切问题。能够确认的是已检查的延迟／取消／包解析分支产生完整有效帧或不应答，没有在这些条件下生成当前那种完整坏校验帧。

## 7. 仍值得查的具体时序点与验证方向

1. **[假设] IMU 50 µs 应答与 HAT 自动回切余量不匹配。** 源码只设定 MCU 何时使能驱动，没有反馈 HAT 是否已释放总线；`BUSY` 瞬时检查也不是跨设备握手。本机实际回切耗时未知。反证／限制：大多数同样 READ 有效，异常不只在最后 checksum，不能只凭 50 µs 数值认定冲突。
2. **[假设] 前一事务结束至下一事务开始缺少足够余量，或异常节点延迟发包。** 双方应用没有明确发送完成＋静默屏障。反证／限制：失败前目标包在主机时序中已相隔 12–19 ms，改序也已收齐舵机帧；当前没有实际线上重叠证据。
3. **[源码核验／假设边界] v0.3 没有参考板 PB7 的 RX_EN 门控。** 固件发送时的 PB7 操作在该板不会断开 PA3 的直接总线回显；源码依靠关闭 USART2 IRQ、发完清 RX 来处理。是否在释放／清 RX／恢复 IRQ 的交界误丢新请求，需要结合实际点位和时间，不能凭代码注释认定已隔离。此机制更直接指向下一请求无应答，尚不能解释主机已经取得的坏包。
4. **[源码核验] 错误文案可改进。** IMU 分支的纯坏包最后统一返回 timeout，而舵机 SYNC_READ 分支会根据 `decoder.bad_checksums` 区分 checksum／timeout。这是明确的诊断信息缺口，修文案不能作为通信修复。

更有针对性的后续对照应一次只改一个条件：记录物理发送完成附近的时刻及包间隔，再分别验证主机发送排空／间隔或 IMU 的应答延迟；所有坏帧继续拒收、保留当前起身保护。仅将每次 poll 的 2 ms 调大，不会增加 MCU 的 50 µs 回切等待；仅放宽整组 20 ms，也不能让固件重发已取消的答复。本轮只给出分析与候选方向，没有改参数、刷机或执行动作。

对照时必须明确间隔的两端：在上一事务结束后、下一条 READ 发出前加间隔，才改变事务之间的距离；READ 已经发出后主机再 sleep，只会推迟主机取数据，不会改变 IMU 固件安排应答的时刻。`tcdrain` 可以作为发送排空的对照手段，但不能据此宣称 HAT 方向已经回切或电气线路已经稳定；实际驱动和线路行为仍需对应证据。
