# 简单 Spec 开发流程（2026-10-23 立项）

功能开发与修改类任务的固定流程：**需求确认 → 文档确认 → 修改方案 → 编码 → 提交**，前一阶段未获用户确认不进入下一阶段。本文件是 [AGENTS.md](../AGENTS.md) 第四节第 8 条的展开说明；与第 4 条（默认不自动提交）相关之处，以第 4 条为准。

## 适用范围

- **适用**：新功能开发，现有脚本 / 固件 / 训练管线 / 板上工具 / 文档工具的功能性修改，跨文件、改接口或改行为的改动。
- **不适用**（不强制套用，按原有规则直接执行并在对应文档落盘）：纯调研与问答、照片/证据归档、硬件核对与排障、上电/接线/刷写操作（仍走安全规则）、单处笔误修正等小改动。

## 五个阶段

| 阶段 | 要做的事 | 出口条件 |
|---|---|---|
| 1. 需求确认 | 复述需求：解决什么问题、给谁/什么用、**不改什么**（负面范围）、验收标准；有歧义先带选项问清，不猜。 | 用户确认复述与验收标准无误。 |
| 2. 文档确认 | 按 AGENTS.md 导航读取相关现行文档与专题调研；列出本次会影响到的现行入口（README / PROGRESS / BOM / 操作单 / 各索引）；核对证据等级（本机实测 / 用户确认 / 规格推断 / 待确认），依赖"待确认"项的先摆出来。 | 用户确认现状理解与受影响文档清单。 |
| 3. 修改方案 | 给出方案：改哪些文件、接口/数据变化、实现步骤、风险与回退、按测试价值原则要做的检查；多方案时给推荐项及理由，不铺开所有选项。方案即 spec 主体，落盘（见下）。 | 用户批准方案。 |
| 4. 编码 | 按批准方案实现，不擅自扩大范围；发现必须偏离方案时回到阶段 3 说明并重新确认；完成后做方案里声明的检查。 | 编码完成，检查通过或如实报告未通过项。 |
| 5. 提交 | 汇报变更清单（文件、行为、遗留项），同步更新受影响现行入口与 `PROGRESS.md` 并互链；按 AGENTS.md 第 4 条默认保留工作区，用户明确要求时才 commit/push 并如实报告结果。 | 变更交付并如实报告状态。 |

## Spec 落盘

- 进入编码前，把阶段 1–3 的结论写入 `docs/specs/<YYYYMMDD-主题>/spec.md`（目录不存在则新建，一个任务一个目录）；后续阶段在同一文件追加更新状态。
- 模板：

```markdown
# Spec：<任务标题>

- 日期：YYYY-MM-DD
- 状态：需求确认 / 文档确认 / 方案已批准 / 编码中 / 已交付
- 需求：<复述、负面范围、验收标准>
- 现状与依据：<相关现行文档、证据等级、待确认项>
- 方案：<改动文件、接口变化、步骤、风险与回退、检查项>
- 变更记录：<实际改动与方案偏差>
- 提交：<commit 短哈希与摘要；未提交则写"未提交，保留工作区">
```

- 小任务（单文件、低风险、无接口变化）可合并记录，不追求每阶段独立成文；但关键决定仍须落盘，不留只在聊天里的结论（与调研落盘规则一致）。
- 与 `docs/references/<主题>-YYYYMMDD/` 的分工：spec 记"要做什么、怎么改"，references 记"查到了什么、证据是什么"；同一任务两边互链。

## 与现有规则的关系

- 提交阶段遵守 AGENTS.md 第 4 条：**默认不自动 commit/push**。"提交"是流程的最后一步，不等于自动触发。
- 检查项遵守第 7 条测试价值原则，只做方案声明且有价值的项目。
- 本流程不构成任何上电、接线、刷写或下单许可；硬件操作仍按对应安全规则执行。
