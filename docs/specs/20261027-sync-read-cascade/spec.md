## 问题

`tools/servo-web/feetech.py`（上游 v0.15.2 同源实现）的 `sync_read` 按**请求列表顺序逐个 expect** 读应答，而 `_read_status(expect_id)` 是**先消费完整帧、再校验应答 ID**：

```python
# 读 FF FF 帧头（60ms 窗口，来谁的帧头都算）→ 读完整帧 → 此后才检查：
if expect_id is not None and sid != expect_id:
    self.stats["bad_id"] += 1      # 帧已被消费，直接丢弃
    raise BusError(...)
```

主机侧没有从机槽位（~300µs/槽）概念。当列表中**任一 ID 缺席或晚答、且其后还有应答者**时：后续第一颗的应答帧落入缺席者的 expect 窗口 → bad_id 丢弃 → 全体错位 → **缺席者之后所有 ID 的应答全部无法收到**。末尾缺席不连累；晚答等同缺席。

## 实测证据（2026-10-27 深夜，独占四步实验）

1. **单舵机轮步骤 3**（200 在线、#34 在线、其余 14 颗离线）：批耗时 294.7ms 逐项对账 = 200 应答 ~1ms + #34 帧被 expect(10) 吃掉（bad_id 1）+ 14 个空 expect 各 20ms 超时——帧到达顺序其实完全正常（#34 严格按槽位等完 14 个空槽才答），仍被吃。
2. **15 颗在线、200 静默轮**：步骤 3 整拍 15 bad_id 连锁全灭；步骤 4 @50Hz×10s **bad_id 5786 ≈ 386 拍 × 15 精确吻合**，IMU 与 15 颗舵机成功率全部 0.0（固定 16 ID 顺序无降级机制时每拍必然连锁）。
3. **历史形态回溯解释**：servo-web 的"3 秒内读不到"警告此前 7 次均为"多颗/15 颗 ×N"形态——单颗丢帧 + 本缺陷连锁判丢即可解释，无需"总线级瞬断"假设（对 10-27 续 2 节"瞬断"解读的进一步降级佐证）。

## 影响面

- **常态（IMU 被 imu_bus 5 帧降级移出列表）**：15 颗舵机自身丢帧率极低（10-22 实测超时 0），顺序链几乎不断——缺陷潜伏，偶发表现为一轮多颗 miss。
- **IMU 在列（混读形态）**：IMU 在第一位且（当前故障配置下）不应答 → 每拍整链崩，15 颗舵机陪葬。**在 IMU 物理层故障修复前，混读形态不可用与此缺陷叠加。**
- 诊断层面：bad_id 计数会吞掉真实帧，逐帧日志（bus log）不含被吃帧（bad_id 路径无 trace 行）——分析丢帧时需注意此盲区。

## 候选修复方向（立项时评估，未批准）

1. 缓存乱序帧：读到 sid≠expect 时暂存帧（按 sid 归位），本拍 expect 链走完后补配——不干扰时序，改动局部；
2. 按槽位时刻校验/推进：expect 前先按 n×槽宽推进时间窗，杜绝"谁的帧都消费"；
3. 最小语义修正：缺席者只丢自己（读到错帧时直接跳过该 expect 而不消费后续）——不可行（帧已读入缓冲，不消费则下个 expect 读到半帧），仅列出说明为什么 1/2 才是有效方向。
