# 2026-11-01 先舵机后 IMU：三次复现与顺序对照

> **历史任务**：2026-11-01 换上新单口板后，相关通信补丁已撤回，见[当前回滚 Spec](../20261101-restore-mixed-sync-read/spec.md)。以下实验、安装与验收按原日期保留；环境及 Studio 显示适配不在撤回范围。

## 需求与授权

用户当轮明确要求：“先再试三次……对比跟 servo-web 在等待时间和判错的逻辑……然后尝试跟 servo-web 一样，先发舵机的，再发 IMU 的。”沿用此前已托稳的现场条件。本指示已明确给出三次基线、比较内容和修改方向，作为本任务需求、文档依据及具体顺序修改的授权，不重复询问已授权步骤。

目标：在原 robotd 上再采三次 `hold-home`，核对失败阶段和原始校验字节；随后仅把 v0.3 遥测顺序换成舵机 SYNC_READ → IMU 单播 READ，做一次同样原生动作对照。

不扩大：不改变零位、HOME、方向、扭矩/位置写法、3 秒过渡、50 Hz、20 ms 总遥测截止、错误后卸力条件、固件或接线；暂不照搬 servo-web 放宽后的逐帧等待和缺失容忍。三次基线后先分析；对照只授权本任务必要的一次，遇异常结束并卸力。

验收：所有尝试有独立防重复标记、原始串口记录、RPC 结果、前后诊断与卸力回读；报告是否同阶段/同字节，并区分样本事实和独立性限制。新顺序通过相关传输测试及构建后部署，先检查启动状态，动作结束确认卸力和 Studio 可用；若对照无改善则恢复已知旧版，并保留试验补丁/二进制来源记录。

## 修改方案

1. 基线三次复用已执行的一次性 RPC 采集器，仅输出名／授权计数不同；每次前后原始 READ 回读与服务恢复，必要失败即中止，不重跑已发送尝试。
2. 在 v0.3 专用 `imu_to_dxl_telemetry` 的严格完整读取入口（当前 commissioning / read-only 实际路径）中先发舵机 `sync_read_window`，随后发 `imu_to_dxl_read`；两半共享原始 started/deadline。合并双方统计，最终只有完整且满足现有数据检查的结果可用。**保留允许部分舵机反馈的另一路旧顺序**：该路原先可在预算末尾接受缺舵机，若直接倒序会在预算耗尽后才读 IMU，混入保护语义变化；当前站姿复现不走它。不将部分/坏帧变成成功，不改其他板分支。
3. 使用独立增量补丁与 build 标识，留存原版；只运行覆盖顺序、坏帧、超时/统计的必要测试及 arm64 编译。服务停启和程序替换在卸力状态执行。
4. 新顺序做一次 bounded `hold-home` 对照，保持和基线相同采集。若没有改善则恢复旧版；成功一次也只报告样本成功，不宣称可靠性验收。
